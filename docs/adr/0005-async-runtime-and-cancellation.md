# ADR-0005 비동기 실행과 요청 취소

- 상태: 제안 (SPIKE-01에서 기본 동작 확인)
- 일자: 2026-10-22
- 관련: PRD-LLM-004, PRD-UI-007, SRS 10절

## 맥락

- ratatui Inline 뷰포트는 생성, 리사이즈, `clear()` 때 커서 위치 질의(`ESC[6n`) 수행.
- 커서 위치 응답은 터미널 입력 스트림으로 도착. 다른 스레드나 비동기 스트림이 동시에 입력을 읽으면 경합 발생 (ratatui #2640, research/rust-crates.md 2절).

## 결정

- UI 스레드(주 스레드) 1개가 터미널 입력 읽기(`crossterm::event::poll`, `read`)와 렌더링, 커서 질의를 전담.
- 네트워크 작업(LLM 요청, 토큰 갱신, 콜백 리스너)과 시그널 수신은 tokio 멀티스레드 런타임(작업 스레드 2개)에서 실행, 결과는 채널로 UI 스레드에 전달 (`try_recv`).
- poll 대기 시간: 요청 중 120ms (진행 표시 갱신), 유휴 500ms.
- 각 요청에 단조 증가 `RequestId`와 취소 토큰 부여. 취소 시 토큰 신호와 작업 `abort`로 HTTP 연결 종료, 이후 도착한 결과는 ID 불일치로 폐기.
- 동시 진행 요청 최대 1개 (TUI 기준).

## 근거

- 커서 질의와 입력 읽기를 같은 스레드에 두어 경합 원인 제거.
- SPIKE-01 esc 케이스: 요청 중 Esc 취소 후 Mock 응답 미반영 확인.
- ID 기반 폐기는 취소와 응답 도착 경합에서도 결정적 동작 보장.

## 대안

- (a) crossterm `EventStream` + `tokio::select!`: 내부 이벤트 읽기 스레드와 커서 질의 경합 가능성, 기각.
- (b) 별도 입력 스레드 (SPIKE-01 방식): 실험에서 문제는 미관측. 경합 가능성 제거 목적상 (a)와 같은 이유로 기각.
